# Verification Host

The product's verification surfaces are one agent-agnostic host: a reusable workflow that installs and runs a marketplace verdict skill through the `spx` CLI and carries no verdict logic of its own. A verdict here is the skill's structured output — findings for the review gate, the audit carrier for the audit gate — never an approve/reject decision the host imposes. The skill, its source ref, the agent, and the model are caller inputs; an agent adapter translates the shared invocation contract into the selected CLI's authentication, skill installation, tool boundary, and launch shape. The host translates GitHub context into the `spx` CLI's environment contract and owns the output route. Pull-request persistence uses host-set sink variables in the host-owned persistence step.

## Rationale

A verdict surface has two parts that change at different rates and belong to different repositories: the judgment (prompt, taxonomy, finding shape, arbiter) and the CI plumbing (checkout, auth, permissions, comment posting). Binding them into one workflow forces every judgment change through a workflow release and ties a surface to one agent. Sourcing the judgment as a marketplace skill keeps it in `outcomeeng/plugins`, where the `spx/gh-actions.product.md` NEVER assertions govern it, its ref identifies its version, and each agent receives its tuned variant. Reducing the workflow to a host keeps the CI plumbing in this product, where its supply-chain and least-privilege posture is governed by `spx/32-security.enabler`; the host's sanitized-launch invariant below is this ADR's own addition to that boundary.

The `spx` CLI is the deterministic backend the verdict skills call for every non-agentic step — diff computation, verdict validation, aggregation. Persistence is the exception: it carries the write credential, so the host owns that step and the skill never invokes it. The host gives the skill the same judgment inputs in local and CI runs while withholding GitHub-specific environment, credentials, and sink routing; residual filesystem signals remain governed separately by the normalized-workspace boundary below.

The agent is one configuration axis over the single invocation shape declared in `spx/32-agent-invocation.enabler`, generalized from provider/runtime to the agent itself. Each agent resolves its own marketplace-tuned variant of the same skill from the same marketplace, so agent breadth costs a per-agent install-and-invoke adapter, never a per-agent workflow.

The Codex adapter uses ChatGPT-managed subscription authentication rather than an OpenAI Platform API key. The host supplies a Codex access token from its secret boundary to the CLI's supported login command, which creates disposable runner-local Codex state. The raw access token exists only in that preparatory authentication process; the Codex agent process receives the resulting agent home and no access-token environment variable. Ephemeral runner state removes credential persistence and refresh-state transport from the reusable workflow contract.

Authorization and filtering are pre-agent concerns: the host verifies that the pull-request author is a trusted repository actor, then decides whether a verdict is warranted from the changed-file set before paying for an agent run. An untrusted author, empty change, or out-of-scope change starts no agent.

The sanitized-launch discipline is specific to the verification host because its verdict skill must stay CI-agnostic. It does not extend to the mention and general-review surfaces, whose documented contract requires the runner-injected credentials `anthropics/claude-code-action` reads for its early PR-branch `git fetch` (CLAUDE.md Security section); those surfaces are contained at the job-permissions layer, not by an environment scrub.

Alternatives rejected:

- **Baked-in prompt (a workflow carrying its own verdict judgment):** couples judgment to plumbing, forces a workflow release per judgment change, drifts from the governed skill, and binds the surface to one agent. The product forbids restating that judgment; the host makes the cross-reference structural rather than textual.
- **Agent-detects-CI:** letting the verdict skill read `GITHUB_*` itself binds the portable verdict engine to one CI platform. Host-set sink variables keep the skill CI-agnostic and the host the only GitHub-aware layer.
- **One workflow per agent:** duplicates the plumbing and the security posture per agent and contradicts the single-invocation-shape declaration in `spx/32-agent-invocation.enabler`.
- **Action-based agent invocation (`uses: anthropics/claude-code-action`):** a `uses:` step inherits the unsanitized runner step environment — `GITHUB_*`/`RUNNER_*` cannot be overridden by a step-level `env:` block — and performs its checkout, fetch, and agent launch internally, leaving no point at which the host can scrub the environment before the agent launches. The verification host invokes the agent's CLI in a child process with a cleared environment because the action is incompatible with the sanitized-launch invariant.

## Invariants

- For a verdict skill and a fixed diff, the judgment applied and the verdict emitted are identical between a local run and a CI run; the host routes the result but injects no judgment-affecting difference into the skill's *environment or credentials* (ambient differences like agent-credential source, runner OS, and network policy lie outside the skill's judgment and do not bear on this invariant). The host closes three channels by construction: the environment (scrubbed `GITHUB_*`/`RUNNER_*`/`SPX_VERDICT_*`, while admitting `SPX_VERIFY_BASE_REF` and `SPX_VERIFY_HEAD_REF` as non-secret diff coordinates), the in-environment GitHub/CI credential (the runner-injected `GITHUB_TOKEN` and the sink token — never the agent's own credential, which the launch admits), and the sink. A fourth credential channel — the GitHub token `actions/checkout` writes to `.git/config` — is in scope but is not closed by the environment scrub; a separate Verification rule below governs it. Residual CI-only signals a skill could still read from the filesystem — the workspace path, checkout metadata — are not closed by this invariant and would need a normalized-workspace sandbox outside this invariant's scope.
- The `SPX_VERDICT_*` sink contract is entirely host-side and never enters the agent or skill environment: `SPX_VERDICT_SINK` (destination kind), `SPX_VERDICT_REPO` and `SPX_VERDICT_PR` (address), and `SPX_VERDICT_TOKEN` (the write credential — a `GITHUB_TOKEN` scoped to `pull-requests: write` for a pull-request sink) all reach only the host-owned persistence step. The address variables would let a skill detect the CI/PR context as readily as the token would grant it write authority, so both stay host-side and the skill receives neither the routing nor the credential.
- Agent authentication is a host-owned preparatory boundary. Claude admits only its selected credential variable to the Claude subprocess. Codex login consumes the Codex access token before agent launch and creates disposable runner-local Codex state; the Codex subprocess receives that state through its agent home while `CODEX_ACCESS_TOKEN` remains absent from its environment.
- The Codex adapter exercises ChatGPT-workspace subscription entitlement and never routes through an OpenAI Platform API key or the API-key proxy in `openai/codex-action`.

## Verification

### Audit

- ALWAYS: a verification surface installs the verdict skill from a marketplace at a caller-supplied ref and invokes it; the workflow holds no prompt, taxonomy, finding shape, or arbiter of its own ([audit])
- ALWAYS: the skill, its source ref, the agent, and the model are caller inputs, with the agent defaulting to the Claude Code agent ([audit])
- ALWAYS: the host honors the caller-supplied `skill` and `ref` only after the caller workflow at the PR head byte-matches the default branch (the `validate-workflow` gate of `spx/32-security.enabler`) — without that gate a same-repo PR could edit those inputs to install arbitrary judgment code running with agent credentials, since GitHub runs a `pull_request` workflow from the PR head ([audit])
- ALWAYS: the host launches the agent only after the PR author's repository permission resolves to `admin`, `maintain`, or `write`; read-only and fork PR authors skip the agent run to protect agent credentials and token quota ([audit])
- ALWAYS: a production caller pins the skill source ref by full-length commit SHA — the verdict skill defines the judgment and runs with agent credentials, so it is a CI dependency under the SHA-pin supply-chain discipline of `spx/32-security.enabler`; a floating ref (branch or tag) is admitted only for a trusted-boundary preview caller carrying the documented exception marker, mirroring the `# BETA TESTER:` reusable-workflow exception ([audit])
- ALWAYS: a verdict skill reaches diff computation, validation, and aggregation only through the `spx` CLI; persistence is a separate step the host runs — invoking the CLI itself, outside the skill's reach, with the whole `SPX_VERDICT_*` sink contract in that step's environment alone — so the skill never triggers persistence and neither the routing variables nor the write credential enter the agent or skill process ([audit])
- ALWAYS: the host launches the agent and skill with a sanitized environment admitting only the selected agent's runtime credential carrier (`ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN` for Claude, or disposable authenticated agent-home state for Codex), the OS minimum any process needs to run (`PATH`, `HOME`, `TMPDIR`/`TMP`), and the `SPX_VERIFY_BASE_REF` / `SPX_VERIFY_HEAD_REF` diff coordinates — raw preparatory credentials such as `CODEX_ACCESS_TOKEN`, all `SPX_VERDICT_*` sink variables, and all ambient `GITHUB_*`/`RUNNER_*` defaults remain absent — scrubbed at the process level (a child process started with a cleared environment), since a runner injects those defaults into every step unconditionally and a step-level `env:` block cannot override them; so the skill's environment and credentials match a local run by construction rather than by the skill's good behavior ([audit])
- ALWAYS: no GitHub token reaches the skill subprocess through `.git/config` — environment scrubbing alone leaves the checkout token there for a skill with git access to read, so the host ensures the token is absent from the skill's workspace before the subprocess launches, via a dedicated `persist-credentials: false` skill-workspace checkout ([audit])
- ALWAYS: the agent is a configuration axis over the shared invocation shape of `spx/32-agent-invocation.enabler`, each agent resolving its own marketplace-tuned variant of the chosen skill ([audit])
- ALWAYS: a changed-file filter runs before the agent and can decline the run, so an out-of-scope or empty change starts no agent ([audit])
- NEVER: a fork or read-only PR author consumes agent credentials or token quota through the verification host; those PRs skip the agent run unless a trusted-actor opt-in path is explicitly specified ([audit])
- NEVER: a verdict skill reads GitHub-specific environment, or the host routes the verdict by any path other than the host-set sink contract — the skill stays CI-agnostic and portable ([audit])
- NEVER: a surface restates the verdict judgment it cross-references — `plugins/spx/21-spec-tree.enabler/68-reviewing.enabler/21-reviewing-changes.enabler/reviewing-changes.md` for the review prompt, `plugins/spx/21-spec-tree.enabler/68-reviewing.enabler/reviewing.md` for the taxonomy, `plugins/spx/15-merging.pdr.md` for the reviewer-only decision ([audit])
- NEVER: a surface embeds a second copy of the agent-invocation shape, bypassing the shared setup that `spx/32-agent-invocation.enabler` governs ([audit])
- NEVER: the host imposes an approve/reject decision on a skill's output or alters the skill's output contract — the review gate's output stays findings-only, preserving the reviewer-only boundary governed by `plugins/spx/15-merging.pdr.md` (reviewer-only decision) and `plugins/spx/21-spec-tree.enabler/68-reviewing.enabler/reviewing.md` (findings-only rule) ([audit])
- NEVER: the pre-agent filter decides from the push event's changed-file list alone when that decision is security-relevant — a fork PR can spoof that list, so a security-gating filter resolves the changed set through a checkout- or API-based source the PR head cannot forge ([audit])
