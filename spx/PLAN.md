## Deferred / open

The top-level enablers' `[audit]` tags conform; `tests/` directories (for `gh_actions` package logic) and `spx/EXCLUDE` entries (for the declared gates) are created during `/testing` and implementation per that ADR.
- **Declared, not built.** In `spx/54-verification-gates.enabler`, the review gate is implemented; validation, test, and audit are declared and belong in `spx/EXCLUDE` once they carry specs and tests.
- **Per-node decomposition.** Each top-level enabler is a candidate for `/decomposing <node>` as its concerns grow — e.g. `spx/32-security.enabler` into supply-chain / authorization / validation, and `spx/54-verification-gates.enabler` into the four gates. `/authoring` deepens each node's assertions beyond the placeholder compliance rules.
- **plugins/spx cross-reference.** The review gate's prompt (`plugins/spx/21-spec-tree.enabler/68-reviewing.enabler/21-reviewing-changes.enabler/reviewing-changes.md`), taxonomy (`plugins/spx/21-spec-tree.enabler/68-reviewing.enabler/reviewing.md`), and reviewer-only decision (`plugins/spx/15-merging.pdr.md`) are cross-referenced at those paths, never restated.
- **Verification host — governed by `spx/18-verification-host.adr.md`.** The `spec-tree-verification` workflow realizes the first Claude Code branch-preview slice of the ADR: a thin host taking `skill`, the skill's source `ref`, `agent`, and `model` inputs; the `spx` CLI as the deterministic backend; and a pre-agent changed-file filter. The preview host captures the skill's journal-rendered output in the job summary while hosted pull-request comment persistence remains blocked on the upstream `spx` hosted PR delivery command. The existing `spec-tree-review.yml` remains the pre-host shape with a baked-in prompt until `spec-tree-verification` supersedes it for production review runs; ADR 18 declares the resolution path for the baked-in-restatement follow-on recorded under `spx/54-verification-gates.enabler/ISSUES.md` Issue 1's "This repo's follow-on" (that follow-on stays open until the baked-in prompt is actually replaced).
  - **Cross-repo sink contract.** The `SPX_VERDICT_*` sink variables are a contract shared with the `spx` CLI (`outcomeeng/spx`); both repos must agree on the names. `spx/18-verification-host.adr.md` holds the host's side of the contract (the variable list under Invariants); `spx/54-verification-gates.enabler/ISSUES.md` Issue 2 tracks the gap that no single canonical declaration yet spans both repos. The `spx` CLI's hosted-PR verdict-delivery command — which reads these variables to post a rendered verdict to the pull request — is upstream work in `outcomeeng/spx`; it renders verdict projections today but reserves remote pull-request mutation to that not-yet-built command.
  - **Sanitized-launch mechanism (build-time).** `spx/18-verification-host.adr.md` requires the agent/skill step to run without ambient `GITHUB_*` and without any `SPX_VERDICT_*` sink variable (routing and credential alike are host-side). A step-level `env:` block does NOT satisfy this: GitHub Actions injects `GITHUB_*`/`RUNNER_*` into every step and they cannot be overwritten by `env:`, so they would still reach the skill. The scrub must be process-level — launch the agent's CLI directly in a child process with a cleared environment (e.g. `env -i`, or an equivalent wrapper) so the inherited runner defaults never reach it. The passthrough allowlist is minimal but non-empty: the process needs `PATH`, `HOME`, and `TMPDIR`/`TMP` to run at all, plus `ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN` when Claude is selected. Codex admits no credential variable; it reads job-scoped authenticated filesystem state from an agent home outside the checkout. Raw preparatory credentials such as `CODEX_ACCESS_TOKEN`, every `GITHUB_*`/`RUNNER_*` default, and every `SPX_VERDICT_*` variable stay out, so the scrub is both complete and runnable. An `always()` cleanup step deletes Codex state after success or failure before job end, and no cache, artifact, or log carries the state or raw token, so shared self-hosted runners retain no credential surrogate. The persistence step runs as its own process holding the `SPX_VERDICT_*` contract, which the agent process never sees. This rules out invoking the agent through a `uses: anthropics/claude-code-action` step: a `uses:` action step inherits the unsanitized runner step environment (`GITHUB_*`/`RUNNER_*` cannot be `env`-overridden) and performs its checkout, fetch, and agent launch internally, leaving no point at which the host can scrub the environment the agent runs in. The first slice therefore invokes the Claude Code CLI directly rather than via that action; the action is incompatible with the sanitized-launch invariant. Because the host owns the checkout directly (not the action), it closes the second channel — the GitHub token `actions/checkout` writes into `.git/config` — by checking out the skill workspace with `persist-credentials: false`; the CLAUDE.md Security rule 4 exception covers the `anthropics/claude-code-action` workflows, which the verification host does not use, so no rule-4 change is needed for it.
  - **Workspace normalization (build-time, open).** The sanitized-launch invariant closes the environment, credential, and sink channels, but a skill with filesystem/git access can still read CI-only signals — the runner workspace path, checkout metadata — and branch on them. Fully realizing "the skill cannot tell it is in CI" needs a normalized-workspace sandbox (stable path, scrubbed `.git` metadata) the host does not yet specify; decide whether to provide it or accept the narrower environment/credential guarantee when the host is built.
  - **Pre-agent filter mechanism (build-time).** `spx/18-verification-host.adr.md` declares the filter as a constraint, not a mechanism, and its NEVER assertion governs the fork-PR `paths:`-spoofing boundary. The mechanism that satisfies it — GitHub-native `paths:` (only where the decision is not security-relevant), a `dorny/paths-filter`-style gate job, or a first `spx` CLI call — is chosen when the host is built.
  - **Agent adapters.** Claude Code is the default adapter. The next host slice adds Codex with a pinned CLI version, Codex-native installation of the caller-selected marketplace skill, ChatGPT-workspace subscription authentication from a host-only `CODEX_ACCESS_TOKEN`, job-scoped runner-local Codex state with always-running cleanup, a sanitized `codex exec` launch, and unchanged journal output. Gemini remains declared for a later adapter.
