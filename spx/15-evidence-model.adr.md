# Evidence Model

The product verifies each assertion through the evidence mechanism that matches its subject: `[audit]` for workflow behavior and security/governance rules no finite automated test can falsify; conformance against `actionlint` + `shellcheck` for structural and shell-injection rules; the in-repo self-test harness (`spx/21-self-test-harness.enabler`) as scenario evidence that a reusable runs end-to-end on real events; and a pytest `[test]` lane over two subjects — deterministic Python in the top-level `gh_actions` package, and a workflow step's inline shell extracted from the workflow and executed against fixture inputs. The pytest-everywhere default from `plugins/spx/15-test-language.adr.md` does not reach workflow nodes, whose YAML carries no importable unit; both `[test]` lanes follow it. Extracted shell is admitted because executing it is a real run of the product's own logic over inputs the lane supplies, which is categorically different from asserting over the YAML that carries it. That package's own test infrastructure — harnesses, generators, and inert fixtures — lives at `gh_actions_testing/` per `plugins/spx/31-outcomeeng.enabler/31-verification.enabler/31-test-verification.enabler/15-test-infrastructure.pdr.md`, outside `spx/` and outside any `tests/` directory; the methodology's own rule against fabricating a top-level `infrastructure → testing → {generators, fixtures, harnesses}` spec subtree still holds.

## Rationale

The product's deliverable is reusable CI workflows other repositories pin and trust, plus example caller templates and a small amount of Python in the top-level `gh_actions` package (e.g. `gh_actions/push_secrets.py`). Evidence that those workflows behave and stay secure is the product's quality guarantee. A mismatched evidence model either leaves workflow behavior unverified — review-only and unfalsifiable — or imposes a code-library test harness on artifacts that have no importable units. Both produce phantom green CI.

Workflow behavior has no importable unit a pytest assertion can exercise; its only honest evidence is a real run plus review of the YAML against the governance rules. Forcing pytest over workflow behavior yields assertions over YAML strings — formatting, not behavior.

A workflow step whose body is inline shell is the exception, because that body is an importable unit in every sense that matters: extract it, feed it inputs, observe its exit status and messages. The self-test harness exercises such a step only along whichever branch a real run happens to take, which for a step that exists to reject a rare condition is the branch that never rejects anything. A step guarding against a condition CI does not reproduce therefore carries no evidence for the behavior it was written for, and an edit that silently stops rejecting that condition produces exactly the phantom-green result this model exists to prevent. Executing the extracted body against fixtures supplies the missing branches without asserting over YAML. The lane also covers a step duplicated across several workflow files, where nothing else establishes that the copies still agree.

Structural and security rules — SHA-pinning, no secrets in `run:` bodies, the `permissions:` shape — are falsifiable by `actionlint` + `shellcheck` against the workflow files; that conformance lane in `ci.yml` is the `[test]`-equivalent for those rules.

The self-test harness is this product's analog of a test runner: it invokes each reusable against this repository on the real event shapes, so a reusable's end-to-end behavior is exercised before it ships.

The `gh_actions` package's deterministic, unit-testable logic — such as the caller-workflow drift checks and the review-findings extractor — gets a pytest lane like any code, with its test files co-located at the serving node's `spx/<node>/tests/`. Where that lane needs test infrastructure — inert fixtures such as captured reviewer-comment payloads, and the harnesses that load them — the infrastructure lives at `gh_actions_testing/{harnesses,generators,fixtures}/` per `plugins/spx/31-outcomeeng.enabler/31-verification.enabler/31-test-verification.enabler/15-test-infrastructure.pdr.md`, never inside a `tests/` directory. Secret provisioning reads the platform keystore and shells out to `gh`, so its behavior is evidenced by `[audit]` (`spx/76-distribution.enabler/distribution.md`) rather than a pytest lane.

The model accepts that workflow behavior leans on `[audit]`, which CI does not enforce: the self-test harness and the `actionlint`/`shellcheck` conformance lane carry the falsifiable load, and audit covers only the residue no run or linter can falsify. It also accepts that the self-test harness's callers reference the reusables — a runtime consumer relationship — while the harness itself is foundational; testability leads, so every node is built and verified against the harness, and that consumer detail stays subordinate to the harness as the verification substrate (`spx/21-self-test-harness.enabler`).

Alternatives rejected:

- **Pytest everywhere** (the methodology default): pytest cannot exercise workflow runtime behavior; the result is string-shape assertions over YAML — phantom evidence. Retained only for the `gh_actions` package.
- **Review-only:** loses the falsifiability `actionlint`/`shellcheck` already provide for structural rules and pytest provides for `gh_actions` package logic. Too weak.
- **Inline shell evidenced by the self-test harness alone:** the harness runs each reusable on real events, so it reaches a guard step's rejecting branches only when a real run happens to fail that way. A step that rejects a rare condition is therefore evidenced along the one branch that proves nothing about it, which is how a guard degrades into decoration without any signal.
- **Moving inline shell into the `gh_actions` package to reach the existing lane:** a consumer pins a reusable workflow and checks out its own repository, so a workflow may not reference this repository's files at runtime. Relocating the logic to reach the test lane would break the self-containment the distribution model depends on; the lane extends to the shell instead.
- **Copying the shell into the test rather than reading it from the workflow:** the copy passes while the shipped step drifts away from it, reproducing in the evidence the same divergence the lane exists to detect between workflow files.
- **A top-level `infrastructure → testing → {generators, fixtures, harnesses}` spec subtree:** the `gh_actions` package's pytest lane does have test infrastructure — inert reviewer-comment fixtures and their loader harness — but `plugins/spx/31-outcomeeng.enabler/31-verification.enabler/31-test-verification.enabler/15-test-infrastructure.pdr.md` forbids fabricating that spec subtree solely because infrastructure exists. The infrastructure is instead governed by the node whose assertions depend on it (`spx/65-review-findings.enabler`) and implemented at the normative `gh_actions_testing/` home. For workflow behavior, which has no importable unit, the self-test harness enabler is the testing-infrastructure analog.
- **Generic `scripts/` directory:** a junk-drawer name accepts any file and gives the product's Python no importable identity. A top-level package named for its domain (`gh_actions`) states what it holds and imports cleanly as `gh_actions.<module>`, matching the top-level-package convention of `outcomeeng/plugins`.

## Verification

### Audit

- ALWAYS: a `[test]` assertion in the tree targets either deterministic Python in the top-level `gh_actions` package or a workflow step's inline shell executed against fixture inputs, its test co-located at the serving node's `spx/<node>/tests/` and named per the canonical `test_<subject>.<evidence>.<level>.py` convention ([audit])
- ALWAYS: a test over inline workflow shell reads that shell from the workflow file it ships in and executes it, so the evidence follows an edit to the shipped step rather than a copy that can drift from it ([audit])
- ALWAYS: a step whose inline shell is duplicated across workflow files carries evidence that every copy agrees, since nothing else establishes that a fix applied to one reached the others ([audit])
- ALWAYS: the `gh_actions` package's pytest-lane test infrastructure — harnesses, generators, and inert fixtures such as captured reviewer-comment payloads — lives at `gh_actions_testing/{harnesses,generators,fixtures}/`, outside `spx/` and outside any `tests/` directory, per `plugins/spx/31-outcomeeng.enabler/31-verification.enabler/31-test-verification.enabler/15-test-infrastructure.pdr.md`; a `tests/` directory holds only typed assertion files ([audit])
- ALWAYS: a reusable workflow's end-to-end behavior is evidenced by a self-test caller in `spx/21-self-test-harness.enabler`, not by an assertion over its YAML ([audit])
- ALWAYS: structural and shell-injection rules (SHA-pinning, no secrets in `run:`, the `permissions:` shape) are evidenced by `actionlint` + `shellcheck` conformance in `ci.yml` ([audit])
- NEVER: a workflow node carries a `[test]` assertion that asserts over workflow YAML strings rather than executing something — matching the text of a step, its keys, or its ordering is formatting evidence, and the extracted-shell lane above is admitted only because it runs the step's logic and observes what that logic does ([audit])
- NEVER: the product fabricates a top-level `infrastructure → testing → {generators, fixtures, harnesses}` *spec subtree* solely because test infrastructure exists — the infrastructure is governed by the node whose assertions depend on it and implemented at the `gh_actions_testing/` home above; the self-test harness enabler is the testing-infrastructure analog for workflow behavior ([audit])
- NEVER: an assertion carries `[eval]` — this product ships no LLM-graded output of its own; the agent's review behavior is governed by `plugins/spx/21-spec-tree.enabler/68-reviewing.enabler/21-reviewing-changes.enabler/reviewing-changes.md` and cross-referenced, so the `[audit]`, `actionlint`/`shellcheck` conformance, and `gh_actions`-package-scoped `[test]` lanes above cover every assertion ([audit])
